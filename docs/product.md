# 제품 계약

## 문제와 가치

프론트엔드 개발자, PM, QA, 최종 사용자가 보낸 오류 제보는 시각·환경·실제 요청이 빠지거나 관측과 다를 수 있다. 백엔드 담당자는 반복해서 자료를 요청하고 로그·코드·배포 버전을 찾아야 한다. TraceBridge는 **거친 제보를 검증 가능한 사건으로 바꾸고, 책임자에게 적절한 범위의 조치 결과를 전달하는 서비스**다.

가치는 모델이 긴 답변을 쓰는 데 있지 않다. 제보 접수, 사건 상관, 근거 수집, 분류, 담당자 라우팅, 권한에 맞는 작업 실행, 검증, 기록과 후속 제보 재사용을 연결하는 데 있다. 같은 자료에 접근할 수 있는 기존 코딩 에이전트+수동 제보 처리보다 실제 시간 또는 오류율을 줄여야 독립 서비스 가치가 있다.

## 사용자와 권한의 차이

| 역할 | 필요한 경험 | 기본 권한 |
| --- | --- | --- |
| 제보자(익명·외부 사용자 가능) | 자연어와 선택 첨부로 제보하고, 본인 제보의 공개 가능 상태를 확인 | 제보 생성, 본인에게 허용된 상태 조회. 내부 로그·코드·다른 제보자 정보 접근 없음 |
| 인증된 팀 제보자(PM·프론트·QA) | 제보와 실제 관측의 차이, 추가 질문, 결과 확인 | 소속 프로젝트에서 허용한 진단 요약 확인 |
| 서비스 담당자·온콜 | 근거·중요도·담당 범위·수정안을 검토하고 피드백 | 담당 프로젝트의 상세 사건·승인된 변경 검토 |
| 프로젝트 관리자 | 연결기, 코드 소유자, 자동화 단계, 알림 대상, 보관 정책 설정 | 프로젝트 범위 구성·정책 변경. 모든 변경은 감사 기록 |
| 운영자·보안 담당 | 다중 프로젝트 운영과 보안 사건 처리 | 별도 부여된 조직 범위 권한. 일반 담당자와 다른 접근 통제 |

**불특정 다수**는 제보 접수 대상의 폭을 뜻한다. 조사 도구와 수정 권한은 프로젝트 소유자의 설정과 실제 인증·인가로 정해진다. 익명 제보도 공개 접수 정책이 있는 프로젝트에서만 받는다.

## 제품 기능

1. **접수와 상관:** 자연어 지시, 거친 증상, 사진만 있는 제보, 프론트 오류 캡처, API 실패, 알림, CI 실패, 보안 도구 결과가 동일한 `Report` 계약으로 들어온다. 기술 메타데이터를 제보자 필수 입력으로 요구하지 않는다. 사진에서 읽은 문구와 시각적 해석은 출처가 붙은 제보 단서이며 서버 원인의 확정 증거가 아니다. 가능한 경우 요청 ID·시각·환경·경로·프론트 빌드 버전을 자동 첨부한다. 같은 원인의 여러 제보는 하나의 사건에 묶되 제보자별 상태와 알림 권한은 유지한다.
2. **관측 대조와 분류:** 제보의 주장과 실제 응답을 분리한다. `기대된 동작`, `입력/사용법 불일치`, `호출자-서버 계약 불일치`, `제품 코드 결함`, `인프라/DB 문제`, `보안 의심`, `판단 불가`를 구분한다. 4xx라는 이유만으로 제보자 실수라고 단정하지 않는다.
3. **중요도와 책임 영역:** 관측된 영향 범위·빈도·환경·데이터 위험·고객 영향으로 중요도를 제안한다. 소유자 매핑과 프로젝트 정책으로 작업 에이전트 역할, 담당 팀/온콜, 제보자에게 보낼 메시지를 결정한다. 모델의 제안만으로 P0 지정이나 권한 상승을 확정하지 않는다.
4. **조사와 조치:** 근거가 부족하면 최소 질문을 하고 보류한다. 명확한 사용법 문제면 설명을 제공한다. 수정 대상이면 정책이 허용하는 수준에서 재현, 격리된 코드 변경, 테스트, 검토, 선택적 배포 후 확인까지 진행한다.
5. **기록과 재사용:** 사건의 근거·원인·실행·검토 결과를 짧게 남긴다. 다음 유사 제보에는 과거 사건을 검색 단서로 사용하고 현재 자료로 재검증한다.

## 제품 범위와 후속 영역

초기 도메인은 웹/API 프로젝트의 오류와 잘못된 사용 보고다. 다중 조직·다중 프로젝트, 주기적 테스트, 코드·API 전체 스캔, 취약점 진단, 운영 배포 자동화는 제품 아키텍처가 수용해야 하지만 단계적으로 제공한다. 전체 API 능동 스캔이나 보안 취약점 확정을 일반 오류 접수와 같은 권한으로 실행하지 않는다. 도구가 낸 경고는 영향과 재현이 확인될 때까지 후보로 취급한다.

자동 해결은 **설정 가능한 능력**이다. 서비스가 항상 자동으로 코드를 고치는 것은 아니다. 프로젝트별 허용 수준·변경 위험·증거·검증 결과에 따라 안내만 하거나, 수정안을 준비하거나, 정해진 조건에서 자동 적용·배포 후 보고할 수 있다. 세부 게이트는 [권한과 자동화 정책](policy-security.md)에 있다.

## 제품 성공의 증거

- 제보자가 로그·코드·DB 자료를 수동으로 복사하지 않아도 관련 사건을 찾는 비율이 높아진다.
- 잘못된 원인 확정과 불필요한 백엔드 수정이 줄고, 증거 부족을 올바르게 보류한다.
- 담당자에게 전달되는 근거·변경·검증 내역이 재현 가능하다.
- 같은 자료 접근 권한을 가진 기존 코딩 에이전트/수동 워크플로와 비교해 조사 시간, 왕복 질문 수 또는 검토 시간이 줄어든다.
- 프로젝트 정책을 넘는 자동 작업, 민감 자료 노출, 검증되지 않은 성공 보고가 발생하지 않는다.

이 기준을 만족한다는 주장은 [평가와 운영](evaluation-operations.md)의 비교 결과로 뒷받침한다. 제품 약속과 현재 데모의 차이는 [현재 구현과 간격](current-state.md)에 따로 기록한다.
