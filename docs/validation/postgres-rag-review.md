# PostgreSQL·RAG 재검토와 수정

2026-09-29, Windows / Python 3.12.7 / PostgreSQL 18.6 / pgvector 0.8.6. 초기 **595개 통과** 기록만으로 실사용 경계를 충분히 검증했다고 볼 수 없었다. 정상 경로 외에 검색 중 검토 변경, 워커 중단·취소, 잘못된 요청, 프로젝트 참조, 구버전 이전, 기존 스키마 업그레이드를 다시 검토했다. 초기 검증 기록은 [그 시점의 기록](postgres-rag.md)으로 보존한다.

## 발견한 결함과 수정

| 중요도 | 문제와 영향 | 수정·검증 |
| --- | --- | --- |
| P1 | 키워드 후보 선정 후 임베딩 호출 중 카드가 정정되면, 변경된 카드를 이전 검색 점수로 반환할 수 있었다. SQLite는 반환 직전 반려도 누락했다. | 후보의 검토 revision을 보존하고 반환 직전 같은 revision·승인·범위를 확인한다. SQLite/PostgreSQL의 정정·반려 경합을 검증했다. |
| P1 | 색인 워커가 꺼지면 조회는 계속 `RUNNING`을 보여 재시도할 수 없었다. 배치가 없는 늦은 완료는 만료된 임대에도 성공 처리될 수 있었다. | 조회·접수·재시도·완료에서 만료를 복구 상태로 전환한다. 완료와 벡터 쓰기에 유효한 토큰·임대가 필요하다. 취소 API/화면을 추가하고 취소 후 늦은 응답·빈 배치 완료를 차단했다. |
| P1 | 중앙 DB의 단일 ID FK는 카드·벡터·수정·적용·최신 실행의 프로젝트/사건 소속을 보장하지 못했다. | 별도 `20260929_03` 마이그레이션으로 복합 참조를 강제한다. 기존 잘못된 데이터의 업그레이드는 데이터 변경 없이 전체 롤백한다. 복구 후 재실행·기존 승인/결과 보존을 검증했다. |
| P1 | 이력 없는 구버전의 import는 성공해도 별도 verify가 실패했다. 기존 구현은 import 중 이벤트 테이블의 불일치를 통째로 제외했다. | 이력 없는 작업마다 명시적인 이전 시점 기록을 만든다. 원 이벤트는 정확 비교하고 허용된 추가 기록의 상태·epoch·메타데이터를 검증한다. 일부 작업만 구버전인 경우와 변조된 기록도 검사했다. |
| P1 | 잘못된 DB URL이 SQLite 파일 경로로 처리됐다. 연결 오타가 예상치 못한 파일 생성이나 부적절한 오류로 이어질 수 있었다. | 지원 URL·지속 SQLite 파일 경로를 먼저 확인한다. 빈 경로·메모리 DB·디렉터리·지원하지 않는 URL을 시작 전에 거부한다. |
| P2 | 잘못된 도구/결과 형식은 서버 예외를 냈고, 잘못된 호출 제한은 요청 예약 후 실패해 예산을 소비했다. 지원하지 않는 역할·tool choice도 전달됐다. | 도구·메시지·제한·tool choice를 예약 전에 검증한다. 잘못된 요청은 `422`, 외부 호출 0회, 모델 단계/예산 소비 0건이다. 잘못된 결과는 실행 중 상태를 유지하고 저장하지 않는다. |
| P1 | 할당된 다음 revision을 검사하지 않아 결과가 사건 이력을 건너뛸 수 있었다. 최신 작업 조회도 프로젝트를 조건에 포함하지 않았다. | 할당된 다음 revision만 허용하고 최신 작업 조회를 프로젝트/사건으로 제한한다. 같은 사건 ID가 다른 프로젝트에도 있는 경우를 검증했다. |
| P2 | PostgreSQL 수정 이력은 임의 실행 ID로 정렬돼 최신 후보가 뒤에 표시될 수 있었다. | 사건 안에서는 revision, 프로젝트 목록에서는 실행 시각으로 정렬한다. ID 순서와 실제 실행 순서가 반대인 사례를 검증했다. |

추가로 앱 종료·마이그레이션 실패의 연결 풀 정리, 화면의 오래된 재시도 표시 초기화, PostgreSQL 전용 워커의 SQLite 실행 거부를 보완했다. PostgreSQL 검색은 물리 스캔 수처럼 보이던 `scanned` 대신 상위 후보 수인 `candidate_count`를 기록한다. 독립 Vector DB나 추가 외부 서비스는 도입하지 않았다.

## 실행 증거

최종 **632개 전체 회귀 통과, 198.93초**다. 새 재검토 사례는 37개이며, 실제 PostgreSQL 검사는 기존 15개와 이번 15개를 합쳐 30개다. 이전 631개 전체 통과 뒤 마지막 정렬 수정을 포함해 전체를 다시 검증했다. 결과와 소스 해시는 [기계 판독 기록](postgres-rag-review.json)에 기록했다. 재검토 회귀 사례는 [검사 소스](../../tests/test_storage_review.py)에 있다. 전체 로그는 `output/pg-validation/review-final-regression.txt`다. 수정 전 API/정렬 실패, 빌드·데이터 대조 기록도 같은 비공개 로컬 경로에 보존한다.

모든 PostgreSQL 검사는 별도 `tracebridge_test_<UUID>` DB를 사용한다. SQLite 기본 저장도 테스트별 임시 경로로 격리했다. 실제 채팅·임베딩 호출은 없으며 doubles를 사용했다. Windows sandbox의 pytest/pip 임시파일 mode 제한 때문에 로컬 검사·빌드는 승인된 실행 환경에서 수행했다. pip 빌드는 `--no-index --no-deps --no-build-isolation`로 수행했다.

검사가 끝난 뒤 생성한 테스트 DB가 0개 남았음을 확인하고, 포트 55432의 별도 검증 클러스터를 정상 종료했다.

최종 wheel의 세 Alembic revision과 저장소·검색·서버 14개 파일이 현재 소스와 바이트 해시까지 일치한다. wheel SHA-256은 `6c282bd84433fe2ae80ee2996cbcacfe349b72d20a44210686b9a59e57efc180`이다. `pip check`도 통과했다. 빌드와 의존성 검사는 현재 환경의 결과이며, 새 Linux 환경에서의 설치·기동 성공을 뜻하지 않는다. PostgreSQL 복합 FK와 commit 시점 검증은 [PostgreSQL 제약 문서](https://www.postgresql.org/docs/current/ddl-constraints.html)의 동작에 따라 구현했다.

## 기존 데이터와 실운영 조건

최종 전체 검사 후 기존 사건 **2,891건**, 실행 **3,120건**과 7개 논리 테이블을 읽기 전용으로 대조했고 모두 일치했다. 보존된 백업에서 이전에 분리한 테스트 ID만 제외한 원 행과 현재 행을 정확 비교했고, SQLite integrity/FK 검사도 통과했다. 증거는 `output/pg-validation/review-journal-after.json`이다. 운영 DB 이전·재색인·실모델 호출은 실행하지 않았다.

현재 결과는 **소유자 전용 시범의 오류·복구 경계 보완**이다. 완전한 운영 출시로 평가하지 않는다. 아래 조건이 남아 있다.

- 새 PostgreSQL/워커 Linux 이미지 기동, 실제 백업 복원, HTTPS 환경과 PC 재연결 검증
- 허가된 실제 제보의 로그·배포 SHA·계약 연결, 원인 확인과 적용 후 핵심 API/사용자 여정 확인
- 실제 한국어 임베딩의 Recall@2·오적중·지연·호출 비용 측정과 대표 데이터 규모의 실행 계획 확인
- 다중 사용자/팀 인증·인가/RLS 및 자동 배포·서비스 회복

작업 난이도·중요도는 현재 소유자 평가를 사용한다. 기록과 검토를 검색에 재사용하는 지속 개선은 제공하지만, 모델이 자동으로 학습하거나 실제 서비스 회복을 보증하는 기능은 포함하지 않는다. [운영 명령](../guides/postgres-rag.md)을 따라 비공개 환경에서 검증한 뒤 실제 전환한다.
