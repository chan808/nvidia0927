# 공개 운영 점검표

현재 기본 서비스의 코드·로컬 검증 결과와 인터넷 공개, 실모델 품질 검증은 각각 기록한다. 실행 증거는 [기본 서비스 검증](../validation/basic-service.md), 설정 방법은 [공개 제보 사용법](basic-service.md)에 있다.

## 대회 시연

1. 별도 시연 프로젝트에 요청 ID·발생 시각·현재 로그·계약·코드를 등록한다. 실제 서비스 자료와 합성 자료의 출처를 표시한다.
2. 공개 화면에서 모호한 제보를 보내고 추가 질문을 확인한다. 요청 ID와 발생 시각을 답해 현재 관측이 연결되는지 확인한다.
3. 입력 누락, 제품 실패, 자료 충돌을 각각 보여 준다. 안내·수정 후보·보류가 실제 근거에 따라 달라져야 한다.
4. 수정 후보에서는 수정 전 실패와 동일 검사·별도 회귀 통과를 보여 준다. 후보 검증과 실제 서비스 회복을 구분한다.
5. 허용된 비운영 프로젝트만 원본 적용을 시연한다. 테스트 서비스가 새 snapshot을 로드한 뒤 회복 검사를 통과해야 해결로 표시한다.
6. 후보 카드의 PENDING과 회복 카드의 선택적 APPROVED, 재사용 시 현재 근거 재확인을 보여 준다. 실모델 호출 수·검사 시간·실패도 함께 기록한다.

이번 자동 처리 검증은 명시적 테스트 모델이다. 실모델 시연은 실제 호출 결과를 별도 기록하고, 준비된 영상·합성 예시를 실제 해결 결과로 표시하지 않는다.

## 인터넷 공개 전 조건

| 확인 | 완료 기준 |
| --- | --- |
| 배포와 재시작 | 현재 API·웹·PC 버전을 맞추고 새 manifest를 확인. 실제 HTTPS에서 공개 화면·정상 접수·운영자 인증을 검증 |
| 실행 격리 | PREPARE/APPLY_NONPROD는 실제 PC의 Docker 이미지·네트워크/파일/자원 제한에서 수정 전후·회귀 검사를 실행 |
| 권한과 한도 | 공개 서비스 목록, 건별 외부 전송 동의, 현재 정책 철회, 대기·시간당 상한, 프록시의 전체 요청 제한을 확인 |
| 자료 연결 | 허가된 실제 사건의 같은 요청·실행 snapshot·계약·호출자 대조. 부족·충돌·버전 차이가 보류로 남음 |
| 모델 품질 | 상세/모호/오류 제보, 안내/제품 결함/보안 의심, 서빙 실패 사례를 반복하고 잘못된 안내·수정률과 호출 비용을 기록 |
| 회복과 복구 | 적용 후 새 코드를 로드한 실제 API를 관측. 동일 버전 실패는 REOPENED, 버전/관측 부족은 미확인. 중단·중복에서 재적용 없음 |
| 저장과 운영 | 격리된 PostgreSQL 회귀와 실제 배포 환경 백업/복원, 실행기 연결 끊김, 예상 접수량에서 대기 시간·예산 확인 |

현재 자동 원본 적용의 환경은 dev/test/staging이다. 운영 서비스 공개 제보는 조사·후보 준비와 담당자의 배포 검토 절차로 시작한다. GitHub 회귀 workflow의 실제 실행과 새 환경 설치 결과도 공개 전 확인 기록에 남긴다.

## 실패 대응

| 표시·상황 | 운영자가 할 일 |
| --- | --- |
| QUEUED가 계속됨 | PC online·manifest·등록 서비스와 대기 상한 확인. 실행기를 연결하고 같은 접수를 새로 만들지 않음 |
| NEEDS_CONTEXT | 같은 요청을 식별할 동작·시각·요청 ID를 받음. 현재 자료의 완전성과 충돌 확인 |
| UNRESOLVED | 내부 작업의 실패 유형·중단 이유·모델/검사 이력을 확인. 기존 시도를 보존하고 새 조사 조건 결정 |
| NEEDS_REVIEW/WAITING_REVIEW | 위험 평가·정책·허용 경로·diff·전후/회귀 근거 검토. 실제 모델 문장을 승인 근거로 대체하지 않음 |
| APPLIED가 계속됨 | 서비스가 적용 snapshot을 실제 로드했는지, 신고 API·회귀·관측 기간의 근거를 확인 |
| REOPENED | 적용과 실패 이력을 유지하고 현재 증상을 다시 조사. 서비스 배포 절차로 복구 결정 |
| 권한 철회 | 공개 정책을 끄거나 변경. 실행 중 작업은 별도로 취소하고 PC의 중단 확인 후 다음 작업 진행 |
| 접수 토큰 만료 | 기존 접수 조회 권한은 종료. 새 문제는 새 접수로 시작. 내부 사건·작업 이력은 운영자가 보존 |

접수 토큰의 7일 만료는 자료 삭제를 뜻하지 않는다. 현재 사건·카드·감사 이력의 자동 보관 기한/삭제 작업은 구현하지 않았다. 자료량에 맞춘 보관 기한과 정제·삭제 정책은 실제 공개 운영에서 정하고 검증해야 한다. 백업·DB 전환·복원은 [중앙 DB 운영](postgres-rag.md)을 따른다.

## 다음 기능의 순서

1. 실제 사건과 실모델로 현재 기본 흐름을 반복 검증하고 판정·검색 품질의 기준선을 만든다.
2. 승인된 매뉴얼의 공개 가능한 항목을 별도로 검토해 챗봇에 제공한다. 내부 사건 전체를 공개 검색으로 연결하지 않는다.
3. 허가된 endpoint·시나리오·범위와 호출 예산을 가진 읽기 전용 능동 점검을 같은 사건 계약에 연결한다.
4. 재현과 담당자 검토를 갖춘 보안/코드 점검으로 확장한다. 전체 API 호출과 자동 원본 수정의 권한은 별도 등록한다.

세부 입력·검증 계약은 [후속 확장 설계](../design/basic-service.md#후속-확장)에 있다.
