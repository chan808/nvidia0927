# 공개 제보와 자동 처리

기본 흐름은 **제보 → 현재 관측 대조 → 안내/질문/작업 판단 → 허용된 수정·검증 → 사건 지식**이다. 공개 사용자는 운영자 토큰 없이 제보하고 자신의 만료형 접수 토큰으로 상태와 후속 답변만 확인한다.

## 시작하기

1. 기존 프로젝트와 PC 실행기를 등록한다. 수정 자동화를 사용할 프로젝트는 재현·회귀 검사와 수정 정책을 먼저 등록한다.
2. 코드 갱신 후 API·웹·PC 실행기를 다시 시작한다. 등록 PC의 새 manifest가 게시돼야 비운영 자동 적용 항목이 확인된다.
3. **연결된 프로젝트 → 공개 제보와 자동 처리 설정 → 설정 불러오기**를 누른다.
4. 접수 대상 서비스와 사용자에게 표시할 이름, 시간당 접수·답변 및 대기 작업 상한을 선택한다.
5. 설정을 저장하고 **API 서버 주소의 /report/프로젝트ID**를 연다. 예: 로컬 API가 8765 포트이면 http://127.0.0.1:8765/report/my-app.

인터넷 공개에는 기존 HTTPS 프록시를 사용한다. deploy/Caddyfile.control-plane은 /report/*와 인증이 제한된 /v1/public/*를 API로 전달한다. 운영자 화면은 기존 인증을 유지한다. 프록시 뒤 IP 제한을 적용하려면 Uvicorn의 FORWARDED_ALLOW_IPS에 **실제 신뢰하는 프록시 IP/CIDR만** 설정한다. 사용자 입력의 X-Forwarded-For를 프로그램이 직접 신뢰하지 않는다. 공개 HTTPS 배포와 부하 시험은 별도 운영 검증이다.

## 자동 처리 범위

| 설정 | 수행 |
| --- | --- |
| INVESTIGATE | 현재 자료 조사, 검증된 입력 안내, 추가 질문, 미해결 기록 |
| PREPARE | 현재 실패가 연결된 사건에서 등록 정책의 별도 사본 재현·수정 후보·회귀 검사까지 자동 실행. 적용 검토 대기 |
| APPLY_NONPROD | 서버와 PC가 모두 허용한 dev/test/staging의 작은 후보만 원본 적용. 적용 결과 보고 후 등록된 회복 검사 자동 요청 |

외부 NVIDIA 분석은 **프로젝트 소유자 설정과 각 제보·답변의 전송 동의가 모두 필요**하다. 둘 중 하나가 없으면 규칙·로컬 조회·키워드 기억을 사용하고 모델을 이용한 수정은 담당자 검토로 남긴다. 제보자가 수정 정책·모델·도구·환경·권한을 선택하지 않는다. 난이도·위험·중요도는 현재 관측에 근거한 잠정 평가이며 모델의 자신감이나 제보의 긴급 표현으로 권한을 높이지 않는다.

비운영 자동 적용은 기존 PC 정책의 allow_apply: true에 더해 **auto_apply_nonprod: true**와 recovery를 등록해야 한다. 신규 필드는 기본 false다. 현재 자동 적용 후보는 파일 1개·추가/삭제 40줄 이내이고 인증·권한·비밀·결제·스키마 등 관련 변경은 담당자 검토로 남긴다. 이 제한은 범용 변경 안전성을 보장하지 않으며 소유자의 경로 허용·등록 검사·snapshot/CAS 검사를 함께 적용한다.

공개 제보에서 **실모델이 만든 코드를 실행하는 PREPARE/APPLY_NONPROD는 PC의 DOCKER 정책을 요구**한다. 서버와 PC가 각각 검사하며 신뢰 로컬 모드로 조용히 전환하지 않는다. Docker 이미지 준비와 기존 네트워크/파일/자원 격리는 [실제 프로젝트 운영](real-projects.md)을 따른다. 검증 코드가 명시적으로 주입한 테스트 모델에서만 합성 프로젝트의 신뢰 로컬 검사를 허용하며, 공개 요청으로 테스트 모델 여부를 선택할 수 없다.

원본 적용과 서비스 배포/재시작은 별개다. 실행 서비스가 새 코드를 로드하지 않거나 회복 근거가 부족하면 해결로 닫지 않는다. 자동 배포·운영 롤백은 이 설정의 권한에 포함하지 않는다.

## 상태와 사건 지식

- 안내는 같은 요청의 완전한 관측과 입력 주체 대조가 확인된 경우에 제공한다. HTTP 4xx만으로 사용자 실수를 확정하지 않는다.
- 정보 부족은 NEEDS_CONTEXT, 시간·호출 한도/실패는 UNRESOLVED, 민감 변경·정책 변경은 NEEDS_REVIEW다.
- 회복 뒤 새 조사가 실패하거나 만료되면 UNRESOLVED로 표시한다. 이전 회복 성공으로 새 실패를 덮지 않는다.
- 후보 검사 통과는 WAITING_REVIEW, 실제 파일 적용은 APPLIED다. 등록한 증상·독립 회귀·실행 snapshot·관측 기간 검사가 통과해야 RESOLVED; 동일 버전의 실패는 REOPENED다.
- 실패/보류/후보/회복을 기록하고 카드에는 knowledge_quality를 표시한다. 저장과 검색 재사용 승인은 구분한다.
- **회복 검사 성공 카드의 검색 재사용 승인**을 켜면 프로그램이 검증한 회복 성공 카드만 자동 승인한다. 미확인 가설과 실패 카드는 자동 승인하지 않는다. 벡터 색인은 기존 명시 전송·worker 설정을 따른다.

챗봇용 공개 매뉴얼과 능동 API/브라우저/보안 점검은 [후속 설계](../design/basic-service.md)의 별도 입력 경로다.

## 공개 API

    GET  /v1/public/projects/<project_id>
    POST /v1/public/projects/<project_id>/reports
    GET  /v1/public/projects/<project_id>/reports/<report_id>
    POST /v1/public/projects/<project_id>/reports/<report_id>/answers

접수와 답변에는 클라이언트가 안전한 난수로 만든 32~128자 Idempotency-Key를 보낸다. 같은 입력·키의 재전송은 같은 기록을 돌려준다. 짧은 기간의 동일 입력은 작업을 공유하면서 제보별 접수 토큰을 발급한다. 키는 응답 유실 시 접수 토큰을 복구할 수 있는 비밀이므로 URL·공개 로그에 쓰지 않는다.

    {
      "text": "버튼을 누르면 같은 화면으로 돌아와요.",
      "service": "backend",
      "context": {},
      "allow_external_analysis": false
    }

응답의 receipt_token은 해당 접수의 조회·답변에만 사용하는 Authorization: Bearer 헤더로 전달한다. 만료는 7일이고 후속 답변은 접수별 최대 10회다. 기본 IP 상한은 쓰기 10회/분, 조회 60회/분이며 프로젝트별 시간당 상한과 대기/실행/중단 확인 중인 작업 상한도 적용한다. 제한은 DB에 저장하므로 프로세스 재시작·여러 서버에서 공유한다. 정책을 끄면 새 접수·답변과 새 자동 작업을 중단하며 기존 접수의 제한된 상태 조회는 만료까지 유지한다.

접수 상한은 승인된 신규 접수·답변에 적용하며 동일 입력·키의 재전송은 추가 소모하지 않는다. 조회 상한은 유효한 접수 토큰의 성공한 조회에 적용한다. 거절된 요청·잘못된 토큰을 포함한 전체 인터넷 트래픽 제한은 HTTPS 프록시의 별도 운영 설정이다.

브라우저는 접수 토큰을 해당 탭의 sessionStorage에 보관하고 주소에 넣지 않는다. 내부 로그·코드·diff·모델 응답·다른 제보자의 답변은 공개 응답에 포함하지 않는다.

상태 응답의 can_answer는 현재 같은 사건에 후속 답변을 받을 수 있는지 표시한다. 대기·실행·실패·만료된 작업, 철회된 공개 정책, 바뀐 등록 범위에서는 false다. answers_remaining은 남은 횟수이며 현재 답변 권한과 별개다. 공개 화면은 can_answer가 true인 경우에만 추가 설명 폼을 보여 준다.

운영자 설정 API는 기존 운영자 인증이 필요하다:

    GET /v1/projects/<project_id>/service-policy
    PUT /v1/projects/<project_id>/service-policy

PUT에는 expected_revision과 policy를 보낸다. 동시에 바뀐 정책은 409로 거절하고 다시 불러오게 한다. 공개 접수·비운영 자동 적용은 기존 프로젝트에서 자동으로 켜지지 않는다.

## 설정 변경과 중단 복구

공개 정책의 revision이 바뀌면 이전 설정으로 배정된 작업은 새 외부 모델·임베딩 호출이나 수정 후보 실행을 시작할 수 없다. PC는 후보 실행 시작 전 서버의 현재 정책을 확인하고, 서버는 모델·검색 전송 시 다시 검사한다. 원본 적용도 별도 최신 권한 검사를 거친다. 차단된 후보 실행은 실패 원인과 UNRESOLVED를 기록하며 운영자가 현재 조건에서 다음 조사를 결정한다.

실행·자동 적용 허가 조회에도 배정된 임대 번호(epoch)를 요구한다. 작업을 재개해 새 번호가 발급되면 중단된 이전 실행기의 번호는 409로 거절한다. API와 PC를 함께 갱신해 새 프로토콜을 사용한다.

이미 시작한 외부 호출을 취소하는 기능은 없다. 실행 중인 검사를 중단하려면 운영자 작업 화면의 취소 기능을 사용하고 PC의 중단 확인을 기다린다. 공개 접수 설정 변경과 작업 취소는 별도 동작이다.

후보 결과를 저장한 뒤 자동 적용 전에 PC가 중단되면 저장 결과를 재전송하고 적용 검토 대기로 남긴다. 이미 원본을 적용했다면 PC의 영속 적용 영수증을 서버에 보고하고 회복 검사로 이어간다. 중단·재전송 때문에 모델 제안이나 원본 적용을 반복하지 않는다. 긴 작업 이력에서도 자동 판단·적용·회복 감사 기록은 전체 이력에서 확인한다.

대회 시연 순서와 실제 공개 전 조건, 실패 대응은 [공개 운영 점검표](basic-service-rollout.md)를 따른다.
